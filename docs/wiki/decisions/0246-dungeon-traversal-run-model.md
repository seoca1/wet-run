## 컨텍스트 (Context)

### 문제 — 전투 밖의 런에는 결정이 없다

제공된 분석의 근거를 다음과 같이 기록한다. 구현을 다시 분석하거나 새 설계를 확정하는 문서가 아니다.

| 현재 동작 | 근거 | 사라진 결정 |
| --- | --- | --- |
| MATRIX 이동은 보스 방향 최단 경로 BFS로 자동 라우팅 | `web/src/core/state/state_actions_phases.ts:97-149` — `applyMatrixAction`이 `nextHopToward(matrix, currentNodeIndex, bossNode)` 호출 | 분기 선택·조우 건너뛰기·조우 거절이 없음 |
| 보상은 확인만 가능 | `web/src/core/state/state_actions_phases.ts:172-245` | 보상 확인 뒤 자동 전진하여 다음 경로를 고르지 못함 |

따라서 **실제 결정은 전투에만 남아 있다.** ADR-0005는 노드를 “명확한 위치 / **결정점**”으로
정의하고 “한 노드 = 한 결정”을 의도했지만, 그 결정점은 구현되지 않았다
([ADR-0005 §고려한 옵션·결과](./0005-cyberspace-representation.md)).
[핵심 루프 §미시 루프](../../design/core_loop.md)의 “발견 → 해킹? 회피? 전투? 후퇴?”도
현재 자동 이동과는 다르다.

### 별도 던전 — 이동 느낌은 있으나 런의 골격으로는 미완성

`DUNGEON CRAWL`은 별도 메뉴다. `web/src/renderer/menu_main.ts:41-51`에서
`web/src/main.ts:1011-1023`으로 진입하며 런과 통합되지 않는다.

| 공백 | 제공된 분석의 근거 |
| --- | --- |
| 이동 이외의 행동이 없음 | `web/src/main.ts:613-657` — 4방향 이동 + 확인/취소/잭아웃뿐. 공격·사용·상호작용·대기 행동 없음 |
| 이동이 모든 것을 해결 | `web/src/core/dungeon/dungeon_crawler_actions.ts:334-347` — 부딪히면 자동 공격. 픽업 자동 적용·함정 자동 발동·문 자동 열기·계단 자동 하강 |
| 무기·방어구 보상이 무효 | `web/src/core/dungeon/dungeon_crawler_actions.ts:116-121` — 픽업 처리 본문이 비어 있음 |
| 죽어도 런이 끝나지 않음 | `web/src/core/dungeon/dungeon_crawler_actions.ts:49-67` — HP를 절반으로 복구. Pillar 3 위반이며 게임 오버 검사도 좀처럼 발동하지 않게 함 |
| 알람이 위협을 키우지 않음 | 별도 던전 규칙의 알람은 실제 위협 상승으로 연결되지 않음 — 제공된 분석 |
| 시야가 정보 규칙이 아님 | `web/src/core/dungeon/dungeon_crawler_core.ts:85-135` — FOV는 표시 전용, 몬스터 AI가 LOS를 무시 |
| 분기 구조를 잃음 | `web/src/core/dungeon/dungeon_crawler_generation.ts:192-209` — 모든 방을 첫 방에 연결 |

**오너가 좋다고 한 것은 던전의 이동 느낌이다.** 원하는 방향은 “던전처럼 이동하며, 가는 길에
이벤트와 보스를 만난다”이다. 이는 별도 던전의 자동 해결·부활·무효 보상까지 채택한다는 뜻이 아니다.

### 핵심 구조 — 런은 이미 공간 배치된 던전이다

| 이미 있는 정보·경로 | 의미 |
| --- | --- |
| `web/src/core/dungeon/dungeon.ts:29-37` — `Room = { id, x, y, w, h, roomType, label }` | 방의 실제 좌표·크기·종류·라벨이 이미 있음 |
| `web/src/core/dungeon/dungeon_layout.ts:411` — `ProceduralDungeonGenerator` | 런은 `matrix.ts`를 통해 사용하고, 크롤러도 `web/src/core/dungeon/dungeon_crawler_actions.ts:11`에서 가져옴. **생성기는 이미 공유됨** |
| `web/src/core/dungeon/dungeon.ts` — `dungeonToMatrix` | 방과 연결을 `MatrixNode[]`로 바꾸며 **`x, y, w, h, label`을 버리고 그래프 형태만 남김** |
| `web/src/core/types.ts:315-329` — `MatrixNode` | `zone`, `iceIds`, `iceHp`, `reward`, `isBoss`, `adjacent`를 이미 보유 |
| 같은 `MatrixNode.eventKind` | `combat`, `discovery`, `trap`, `cache`, `rest`, `merchant` 조우 구분이 이미 있음 |
| `dungeon.ts`의 `roomType === "exit"` 매핑 | 이미 보스 방이며 `isBoss`와 `wintermute`로 연결됨 |

**결론: 런의 레벨은 이미 방·라벨·이벤트·보스 방을 가진 공간적 던전이다.** 제안의 중심은
새 생성기로 갈아엎는 것이 아니라 **변환 과정에서 버린 정보를 버리지 않는 것**이다.
크롤러는 두 번째 게임이 아니라 **런을 위한 발판**으로 본다. 다만 공간 정보를 보존하는 것만으로
결정이 생기지는 않으므로, 아래 조우 결정 계층이 반드시 필요하다.

이 방향은 ADR-0060의 던전 탐색과 ADR-0103의 “던전이 MATRIX screen의 유일한 렌더러/입력”이라는
원래 의도에 가깝다. **웹 포트는 그 통합을 구현하지 않았다.** 결정 계층이 존재한다는 조건 아래,
이 ADR은 두 결정을 대체하는 것이 아니라 **원래 의도가 유효했음을 구현으로 입증하는 요청**이다.
ADR-0005의 결정점도 같은 조건 아래 복원한다. 기존 결정 본문과 상태는 그대로 둔다.

## 제안 모델

**검토할 모델**: 생성된 방·연결·방 종류·라벨·이벤트·보스 방을 런의 공간으로 유지한다.
플레이어는 그 공간을 타일 단위로 이동하고, 조우에 접촉하면 대응을 결정한다.
이동 자체가 공격·보상 수령·함정 해결·다음 방 진입까지 모두 자동 처리해서는 안 된다.

```text
런 진입 → 생성된 방·통로 이동 → 조우 접촉 → 정보 확인·대응 선택
                                      ├─ Probe / Bypass / Breach / 후퇴
                                      └─ 선택한 행동의 해결 → 런 상태에 반영
                 ↑───────────────────────────────┘
보스 방 도달 → 보스 조우 → 런 결과 / 사망 → 종결
```

- **Probe / Bypass / Breach / 후퇴**는 조우 대응의 동사다. 정확한 비용·성공 조건·창의 길이는
  오너 결정과 튜닝 대상으로 남긴다. 메뉴 이름만 다르고 모두 같은 전투로 이어지면 조건 미달이다.
- **HP·TRACE·보상·덱은 같은 런의 상태**다. 탐색·전투·보상 뒤에도 이월하며 별도 던전 상태로
  격리하지 않는다. 보상 확인 후에는 같은 위치의 탐색으로 돌아오고 자동 전진하지 않는다.
- **깊이 = 위험**: 기존 `ZoneDepth`와 `roomType`을 위협 대역의 근거로 사용한다.
  새 깊이 자원이나 수치 예산을 만들지 않는다.
- **보스 도달은 이동의 결과**다. `roomType === "exit"` 보스 방을 재사용하되 BFS 자동 라우팅을
  제거해야 어디를 거쳐 도달할지가 선택이 된다.
- **죽음은 종결**이다. HP 절반 복구를 가져오지 않는다
  ([Pillar 3](../../design/pillars.md), [핵심 루프 §미션 종료 조건](../../design/core_loop.md)).

## 지켜야 할 6조건

정보와 보상을 각각 검증할 수 있도록, 제공된 실패 표의 “FOV 무시 AI · 무효 픽업”을 두 행으로 나눈다.

| 번호 | 던전의 실패 | 이 모델이 지켜야 할 것 |
| --- | --- | --- |
| 1 | 이동이 모든 것을 자동 처리 | 조우가 **결정**이다 — Probe / Bypass / Breach / 후퇴가 실제로 다른 결과를 만듦 |
| 2 | 죽음이 HP 절반 복구 | **죽음은 종결** — Pillar 3, 같은 런에서 부활하지 않음 |
| 3 | 런으로 되쓰기 없음 | HP · TRACE · 보상 · 덱이 **런 전체에 이월** |
| 4 | 모든 방이 첫 방에 연결 | **BSP 토폴로지 유지** — 생성된 연결과 분기가 실제 이동 경로로 남음 |
| 5 | FOV를 무시하는 AI | **정보가 의미를 가짐** — 가시 정보와 발각·대응 규칙이 일치하며 표시만 가린 채 전지적으로 추적하지 않음 |
| 6 | 무효 픽업 | **보상은 실제 효과** — 장비·자원·덱 상태에 반영되고 다음 조우에서도 유지됨 |

여섯 조건을 충족하지 못하면 “던전 이동 기반 런”이 아니라 실패한 별도 던전을 반복한 것이다.

### 2–5. 정보·위험·깊이·도달

| 포크 | 옵션·판단할 내용 | 추천·선행 조건 |
| --- | --- | --- |
| 2 — FOV | 표시 전용 유지 / 경로·조우 판단에 쓰는 정보 | **정보로만 사용**. 시야를 소비하는 새 자원 예산은 만들지 않음 |
| 3 — TRACE 통합 | `player.alarm` 0–100과 `alarmLevel` 0–5를 별도 위험으로 표시 / 하나의 플레이어 가시 위험 계기로 통합 | **통합이 선행 조건**. 프로그램 비용 누산기와 유휴 알람의 관계를 정하기 전 새 위험 자원 추가 금지. [ADR-0240 열린 질문 (k)](./0240-idle-pressure-and-alarm-loop.md)와 연결 |
| 4 — 깊이 = 위험 | 기존 깊이를 장식으로 유지 / `ZoneDepth`·`roomType`으로 위협 대역 구성 | **기존 깊이를 위협 대역으로 사용**. 구체 수치와 종류 매핑은 미정 |
| 5 — 보스 도달 | 보스 방향 BFS 자동 이동 유지 / 생성된 분기를 플레이어가 이동하여 `exit`에 도달 | **BFS 자동 라우팅 제거**, 기존 보스 방 재사용. 보상 뒤 자동 전진도 제거 |

**추천 묶음**: 조우 C + 정보로서의 FOV + TRACE 통합 선행 + 기존 깊이의 위협 대역화 + 수동 보스 도달.
이는 추천이며 아직 채택되지 않았다. TRACE 통합은 표시만 하나로 덮는 작업이 아니라
두 위험 값의 관계를 오너가 결정해야 하는 선행 조건이다.

## 수락 증거 (측정 기준)

**미실행 — 향후 구현의 수락 게이트다.** 문서 작성만으로 아래 조건을 통과했다고 주장하지 않는다.

| 검증 축 | 제출해야 할 증거 | 통과 기준 |
| --- | --- | --- |
| 실제 분기 선택 | 고정 seed의 분기 하나에서 서로 다른 두 경로를 입력한 재현 기록과 회귀 테스트. 선택 전 정보·선택 입력·방문 방·발생 조우·런 상태를 비교 | **분기 하나에서 실제로 선택이 발생함**. 다른 방/조우 또는 조우 거절·후퇴 결과가 나타나고, 확인만으로 같은 BFS 경로에 합쳐지지 않음 |
| 결정과 이동 분리 | 같은 조우에서 Probe / Bypass / Breach / 후퇴의 상태 전이·해결 기록 | 이동만으로 해결되지 않음. 대응이 구별되고 후퇴로 강제 전투를 피할 수 있음 |
| 공간 정보 보존 | 생성 결과와 런 타일 배치의 방·연결·라벨 비교 | BSP 분기·연결 유지. 모든 방을 첫 방에 재연결하지 않으며 `exit` 보스 방에 이동으로 도달 |
| 정보·보상·이월 | 가시/비가시 조우의 정보·발각 규칙, 장비 획득 전후 효과, 탐색→전투→보상→탐색 상태 비교 | FOV가 판단에 유효. 보상 효과가 존재하고 HP·TRACE·보상·덱이 런에 유지. 보상 뒤 자동 전진 없음 |
| 죽음 종결 | 탐색과 전투에서 HP 0 도달 재현 | 게임 오버·런 종결. HP 절반 복구·같은 런 재개 없음 |
| 유휴 회귀 | `web/`에서 `npm run balance -- --idle-ms 0` / `npm run balance -- --idle-ms 1000`, 양쪽에 `--deck ppl`을 붙인 측정도 제출. 같은 53 missions·100 runs·seeds 1–100·6 grade, 구현 전후 비교 | **`--idle-ms 0`과 `1000` 동일 유지**, 시나리오 표시 header를 제외한 모든 출력 metric 동일. 전후 기준선도 불변 |
| 밸런스 기준선 | 아래 opening/PPL 기준선과 구현 전후 표, [ADR-0229](./0229-grade-curve-rebaseline.md) 판정 | **기준선 재선언·튜닝 없음**. 다른 탐색 경로의 런 결과는 별도 측정하며 기존 전투 기준선 보존의 증거와 섞지 않음 |
| 저장 호환 | geometry가 없는 기존 저장과 새 저장의 로드·이어하기·왕복 저장 증거 | ADR-0185에 따른 호환 정책을 먼저 명시하고 위치·조우·런 상태 복원. 좌표가 없을 때의 처리 미정 상태로 출시하지 않음 |

유휴 0/1000의 현 기준선은 ADR-0239에서 정하고 ADR-0240의 후속 검증에서도 유지한 값이다
([ADR-0240 §최종 양 덱 × 유휴](./0240-idle-pressure-and-alarm-loop.md)):

| Deck | g1 | g2 | g3 | g4 | g5 | g6 |
| --- | --- | --- | --- | --- | --- | --- |
| Opening | 100.0 | 88.3 | 70.5 | 39.5 | 36.2 | 0.0 |
| PPL | 100.0 | 79.1 | 98.9 | 83.0 | 44.4 | 24.7 |

기존 전투 하네스의 수치 보존만으로 새 탐색의 선택을 증명할 수 없다. **분기 선택 증거를 별도로
제출해야 한다.** 기준선이 움직이면 자동으로 재보정하지 말고 원인과 오너 결정 필요성을 보고한다.

## 열린 질문

1. **조우 모델 세부 튜닝** — A/B/C 중 최종 선택, 발각 전 창의 범위·길이, Probe / Bypass /
   Breach / 후퇴의 정보·비용·성공 조건은 무엇인가?
2. **기존 크롤러 규칙의 처리** — 기존 규칙을 교체하고 이동·표시만 재사용하는가, 런이 크롤러를
   통째로 채택하는가? 어느 쪽이든 6조건을 면제하지 않는다.
3. **현재 MATRIX 목록 렌더러** — 제거·대체·보조 표시 중 무엇으로 정리할 것인가?
   ADR-0103의 단일 렌더러/입력 의도와 맞출 구체 방식은 아직 결정하지 않는다.
4. **`eventKind`와 `roomType` 매핑** — 여섯 이벤트 값이 기존 방 종류에 깔끔하게 대응하는가?
   일대일이 아닌 경우 어떤 대응표와 우선순위를 둘 것인가?
5. **공간 정보를 가진 노드의 저장 호환** — geometry 없는 저장을 어떻게 처리할 것인가?
   `MatrixNode` 스키마 변경의 버전·변환·이어하기 정책은 ADR-0185에 따라 확인해야 한다.
6. **TRACE 통합** — 프로그램 비용과 유휴 상승을 하나의 가시 위험 계기에 어떻게 연결할 것인가?
   ADR-0240 (k)의 오너 결정을 먼저 받고 새 자원 추가는 보류한다.

## 영향 받는 항목

### 재사용할 기반

- `ProceduralDungeonGenerator`, `Room`, rooms + edges + `roomType` + `label` — 생성·공간·연결.
- `MatrixNode`의 `eventKind`, `reward`, `zone`, ICE 정보와 기존 보스 방.
- 기존 전투·보상 처리 기반과 런 자원 — **재사용은 자동 해결·자동 전진 유지와 다르다**.
- `web/src/renderer/dungeon.ts`의 타일 표시와 `dungeon_entities`의 기존 FOV 코드 —
  표시 기반을 재사용하되 정보·발각 규칙의 연결은 별도 변경이다.

### 새로 만들거나 바꿔야 할 것 — 오너 결정 이후

- `dungeonToMatrix`·`MatrixNode`에 geometry와 라벨 보존 — 스키마 변경이므로 ADR-0185 저장 호환 확인.
- 생성된 방에 결합된 **런 단위 타일·장소 렌더러**와 이동 입력 연결.
- 조우 결정 메뉴, 자동이 아닌 조우 해결, 발각·후퇴 규칙.
- `state_actions_phases.ts`의 BFS 자동 라우팅과 보상 뒤 자동 전진 제거.
- 종결되는 죽음, 탐색·조우 결과의 런 되쓰기, TRACE 관계 통합.
- 구현 시 회귀 테스트·분기 재현·저장 호환·밸런스 증거, 관련 디자인 명세 동기화.

**비용은 실재한다.** 생성기 공유와 공간 정보 보존은 재사용 근거이지 구현 완료의 근거가 아니다.
표시·입력·결정·상태 이월·저장 호환 작업이 남는다. 일수 단위 공수는 추정하지 않는다.
